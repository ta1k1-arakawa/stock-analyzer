いま、このリポジトリで
何が起きているのか

1つのリポジトリの中で、毎日動いている小さな売買ボットと、その先を探す厳格な研究プログラムという性格の違う2つが並走しています。この文書は、リポジトリと全ブランチの記録から現在地を読み取ったものです。

全体像

2つの層が並走している

稼働中 — main ブランチ
日本株のペーパートレード・ボット

Yahoo Finance から株価を取り、テクニカル指標を作り、LightGBM で「2営業日以内に1%上がる確率」を出す。平日16時にGitHub Actionsが自動実行し、条件を満たせばSlackに通知して結果をCSVに記録します。README に書かれているのはこの層です。

研究中 — v8系ブランチ群
V8 歴史データ研究ライン

「その戦略は本当に儲かるのか」を、統計的に信用できるやり方で決着させるための研究。設計を凍結し、人間の承認（ゲート）を1回ずつ消費しながら進みます。まだデータ取得の入口で止まっており、収益に関する結論は一切出ていません。

ここを取り違えないこと

mainで毎日回っているボットは、研究の結論として採用されたものではありません。過去の研究ライン（V3〜V6）は PROJECT_RESEARCH_CONCLUSION.md で research_status: CLOSED / deployment_status: NO_CANDIDATE（配備候補なし）と結論済みです。mainのボットは、その結論より前から続いている実運用手前の記録用パイプラインという位置づけです。

稼働層

毎日16時に走っている処理

.github/workflows/daily_ai_trade.yml が平日 16:00 JST（cron 0 7 * * 1-5）に起動し、次の順で動きます。

TRAIN
train.py — モデル学習2020-01-01以降の株価で、銘柄ごとにLightGBMを学習。モデルは毎回作り直し、Gitには保存しません。
PREDICT
main.py → src/predict.py — 予測最新データで「買いシグナル確率」を計算。11個の特徴量（SMA乖離、RSI、MACD、ボリンジャー位置、ATR、ADX、騰落率、出来高変化）を使用。
NOTIFY
src/notifier.py — Slack通知確率がしきい値（既定0.15）以上で、notify_slack: true の銘柄のみ通知。
LOG
src/tracker.py — 結果記録シグナルを data/trade_log_<code>.csv に PENDING で追加し、2営業日後に損益を確定して DONE へ。CSVはActionsが自動コミットします（"Update trade log [skip ci]" の大量のコミットはこれ）。

背景

V3〜V7で分かってしまったこと

研究ラインは、モデルを良くする前に評価器そのものを信用できる状態にするところから始まっています。初期の評価には、銘柄ごとに同じ資金を二重に使う、未来データが混ざる、学習ラベルと実際の約定条件がずれる、といった利益を過大評価する欠陥がありました。それを潰したのが evaluator-v2.0 です。

その厳密な評価器の上で LOOP-000〜004 を回した結果は、PROJECT_RESEARCH_CONCLUSION.md にこう記録されています。

実験内容判定
LOOP-000確率順の基準戦略BASELINE
LOOP-001実現収益率の回帰REJECT
LOOP-002期待payoff順位REJECT（月次勝率未達）
LOOP-003リスク調整スコア当時ACCEPT → 後の監査でスコアの意味不整合が判明し配備不可
LOOP-004校正済み期待収益REJECT
V4メタラベル分類器NOT_PROMISING（AUC 0.508）
V5-A / A2 / Bポートフォリオ・ストップ・ランカーいずれも NOT_PROMISING

研究終了報告の結論

further_loop_on_same_data: PROHIBITED — 同じデータで改良を回し続けることを自ら禁止したのが最大のポイントです。何度も見たデータで良い成績が出ても、それは偶然を拾っただけかもしれない。だから次の研究をやるなら「新しい仮説・新しい事前登録・一度も見ていない評価データ」が要る、と自分たちで縛りをかけました。

その縛りを満たすために作られたのが、V7（未来に向けて記録だけ取る前向き研究）とV8（過去データで探索するが、確認は未使用銘柄だけで行う研究）の2本です。両者は相互に参照禁止で、完全に分離されています。

V8の設計

V8がやろうとしていること

V8の目的は「バックテスト利益の最大化」ではなく、コスト差引後に再現性のあるプラス期待値を持つ戦略を1つ見つけることです（V8_HISTORICAL_RESEARCH_DESIGN.md §2.2）。そのために、日本株の universe を役割の違う塊に分割します。

ブロック銘柄数役割
T0300過去研究で既に見てしまった銘柄。仮説を思いつくためだけに使い、成績の証拠能力はゼロ（evidential_weight = NONE）
T1300新規の検証用。開けられるのは1回だけ。開けた瞬間に「使用済み」になる
T2300封印したままの最終ホールドアウト。候補1つだけを最後に1回試す
T3 / T_spare300 / 残り予備。将来別の仮説を検証する必要が出たとき用

この「一度しか開けられない」を機械的に守らせるために、実行の各段階に人間のワンショット承認（ゲート）が置かれています。ゲートは通信の直前に領収書（receipt）を発行して消費され、消費後にプログラムが落ちても承認は戻ってきません。同じ研究IDでのリトライは禁止で、やり直したければ番号を進めた新しい研究（successor study）を立てるしかない ── これがv8系ブランチが V8B, V8C, V8D… と増えていく理由です。

役割分担も AI_RESEARCH_EXECUTION_RULES.md で明文化されています。人間が最終権限（ゲート）、ChatGPTが研究設計と判断、Claude Code / Codex が実装・実行・記録。実行側は凍結済み設計の曖昧さを勝手に解釈してはならない、というルールです。

現在進行中

V8 から V8J へ ── 9回連続の BLOCK

2026-08-09にV8の設計が凍結されてから今日までの2週間で、研究は9回「閉じて」います。重要なのは、そのどれも戦略が負けた記録ではないことです。全て、本命のデータ取得にたどり着く前の取得基盤・記録契約・実行環境の失敗で、各終了記録には strategy_failure=false / profitability_failure=false が明記されています。

V8I
BLOCK_CLOSEDpandas 未インストール

V8J
設計草案凍結前・ゲート未消費
現在ここ ── 「実行環境が証明されるまでゲートを消費しない」
科学的な方法論はV8Iから一切変更なし（scientific_methodological_change=NONE）。追加したのは運用上の前提条件1つだけ：専用の .venv-real-execution で scripts/check_real_execution_env.py が終了コード0を返し、環境ロックとフリーズ記録のハッシュが一致すること。これが機械的にPASSしない限り、JPXへの1回の通信もゲート消費も行わない。
現在地

いま止まっている場所と、次の一手

0
V8系で完了したデータ取得
0
開封された検証ブロック
0
V8系で測定された損益
9
閉じた研究ID（V8〜V8I）

V8系はまだ「銘柄リストの元になるJPXの公式スナップショットを1回取ってくる」段階にいます。その先に、非公開パーティションの生成 → 株価の生データ取得 → Layer A（仮説探索）→ Layer B（T1で1回だけ検証）→ Layer C（T2で最終1回）と続きますが、どれも未着手です。

次の一手は、V8J草案に対するGPTの独立レビューと人間の設計凍結承認（V8J_DESIGN_FREEZE_APPROVAL）です。凍結後に環境チェックがPASSして初めて、V8Iで失った1回の取得をV8Jとしてやり直せます。

この2週間の教訓を一行で

失敗の中身は「戦略が弱い」ではなく「取得基盤と実行環境が、一発勝負に耐えるほど固まっていなかった」。V8Jが環境の事前証明を足したのは、この直接の帰結です。

用語

記録に頻出する言葉

gate
人間が1回だけ与える実行許可。通信や封印データへのアクセスの直前で消費され、消費後は失敗しても復活しない。
receipt / evidence
ゲート消費の証跡。receiptは通信「前」に分かる値だけ、evidenceは通信「後」の結果を書く。V8Hはこの2つが1つの文書に混ざっていたことで差し戻された。
BLOCK_CLOSED
その研究IDは失敗して永久に閉じた、という終了状態。リトライ・ゲート再利用・記録の書き換えは全て禁止。
successor study
閉じた研究を継ぐ新しい研究ID。前の結論や記録には一切手を触れず、方法論だけを引き継ぐ。V8B〜V8Jは全てこれ。
evidential_weight
= NONE
「この数字は証拠として使ってはいけない」という印。既に見てしまったデータ（T0）の成績に付く。
PRE_GATE /
POST_GATE
失敗がゲート消費の前か後か。前ならやり直せる、後なら研究IDごと終わり。V8Iは後だった。
T0 / T1 / T2 / T3
300銘柄ずつの universe の分割。既出・検証用・最終封印・予備。
案内

自分で追いかけるときの順路

  • 稼働中のボットを知りたい → main ブランチの README.md と config.yaml。
  • なぜ研究をやり直しているか → PROJECT_RESEARCH_CONCLUSION.md（V3〜V6の終了報告、日本語）。
  • V8の全体設計 → まず V8_START_HERE.md、次に V8_STATE.json、詳細は V8_HISTORICAL_RESEARCH_DESIGN.md。
  • いまの最前線 → ブランチ v8g-private-partition-locator-successor-design（最新の文書群がここに集約）の V8J_SOURCE_SNAPSHOT_ENVIRONMENT_SUCCESSOR_DESIGN_DRAFT.md。
  • 各研究がどう終わったか → V8*_TERMINAL_ADJUDICATION.json と V8*_EXECUTION_INCIDENTS.md。
  • AIと人間の役割分担ルール → AI_RESEARCH_EXECUTION_RULES.md、実行手順は AI_REAL_EXECUTION_RUNBOOK.md。

補足：ブランチ名は研究IDと必ずしも一致しません。V8H〜V8Jの文書はいずれも v8g-… ブランチ上に置かれています。日々のログ更新（"Update trade log [skip ci]"）は main にのみ入り、研究ブランチとは独立です。

この文書は、リポジトリの全ブランチ（main および v3〜v8系）に含まれる設計文書・終了記録・実行記録・CSVログを読み取って構成したものです。数値は参照した時点のファイル内容そのままで、推定値は含みません。

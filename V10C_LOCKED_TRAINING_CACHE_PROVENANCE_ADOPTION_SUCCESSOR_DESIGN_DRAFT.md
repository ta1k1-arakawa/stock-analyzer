
## 1. Boundary and purpose

V10B remains terminally blocked. Its acquisition content is mechanically
valid, but the Phase-B direct process-exit-code evidence is missing. V10C
does not repair, retry, or reinterpret V10B and does not infer that the
missing evidence was unnecessary. In particular, the observed V10B success
count of 283 does not recover the historical V9_009 training cache.

V10C is a new, prospective provenance-adoption study. Its sole purpose is to
determine, offline and without reacquisition, whether the already
content-locked V10B durable artifact set can be adopted as a new V10C
training-input provenance identity. It introduces no scientific result and
does not alter the inherited V4/V9 methodology.

The following remain outside this design: T0, evaluation, model fitting,
backtesting, profitability analysis, holdout inspection, and any access to
prices, outcomes, targets, labels, returns, or model-relevant data.

## 3. No reacquisition and no scientific reinterpretation

V10C performs no network request. Yahoo refetch, a second V10B acquisition,
provider substitution, date-window substitution, ticker substitution,
favorable subset selection, retry, and refetch to change the observed
283/17 partition are prohibited. The existing durable attempt state is never
deleted, reset, overwritten, resumed, or repaired.

The V10B manifest's terminal acquisition contract remains historical and
immutable. V10C's adoption contract is a new offline acceptance contract;
its result is provenance adoption or a closed failure, not a retroactive
V10B adjudication.

## 4. Frozen offline adoption acceptance rule

The rule below is frozen before any future implementation or execution. A
V10C PASS requires every condition; there is no partial PASS and no
executor-selectable alternative.

### 4.1 Governance and provenance

The offline validator must first verify the authoritative repository and
branch, a clean tree, and exact reviewed implementation provenance bound to
`b2172723df28b3edfce386c77ee79ce38a716925`. It must verify the exact
V10B terminal adjudication Git blob
`5d1d83fb6bdf1fbe0630e9158c9d039b2e486796` and bind it to the V10B
terminal adjudication commit and successor candidate. The attempt receipt
must have raw SHA-256
`44387e68bfc5de8bf54de8ca9694ba9f12bad2be779224946888eaea36d96eb7`, and
the manifest must have raw SHA-256
`887c031a004f91a080fa53ab511711fff92c92527cb119878ab2c295ee13cd44`.

The validator must confirm that these are the exact candidate bytes. It may
inspect metadata and hashes only; it does not need to parse raw price
payloads.

The V10B acquisition implementation SHA
`b2172723df28b3edfce386c77ee79ce38a716925` is predecessor provenance only.
It is not the reviewed implementation SHA of a future V10C offline-adoption
validator. Every future real V10C adoption execution must bind its executing
validator to a separate exact GPT-reviewed V10C implementation SHA. That
SHA is unknown at design time and may be supplied only after the V10C
validator implementation receives GPT exact-SHA PASS.

Before any locked payload byte is read, the future validator must verify the
authoritative repository identity, authoritative branch, clean working tree,
local HEAD equal to that exact GPT-reviewed V10C validator SHA, and the
authoritative remote branch/ref equal to the same SHA. It must also verify
the frozen V10C design blob, reviewed freeze-approval provenance, and the
complete V10B predecessor/candidate ancestry listed above. No unreviewed
validator implementation may execute adoption.

### 4.2 Manifest and fixed-source binding

The candidate manifest must validate its exact frozen V10B schema and field
set, including `V10B_TRAINING_CACHE_MANIFEST_V1`, the fixed V4 universe and
canonical ticker order, Yahoo Finance chart as the provider, the frozen
query/range, the terminal `complete=true` semantics, and the canonical
payload-entry-list hash algorithm. The fixed universe identities remain the
V4 CSV SHA-256
`d40b1fcfd824822c7511f0d4f99445640706b7f5dfae08155636624704c41997` and
ticker-list SHA-256
`12777a83f259cd885ebb828e0ce895a5bf53be37c27928c1a487f629002ce4f7`.

The manifest must be complete, and its accepted/failed partition must be
mechanically exhaustive and disjoint:

```text
successful_ticker_count = len(payloads) = 283
successful_ticker_count + len(failed_tickers) = 300
accepted_ticker_set ∩ failed_ticker_set = empty
accepted_ticker_set ∪ failed_ticker_set = exact FIXED_V4_300 set
```

The observed count is checked for exact candidate identity, not imposed as
a methodology threshold. Failed membership is accepted only as the
already-locked observed complement; it cannot be edited or improved.

### 4.3 Locked payload closure

All 283 locked payload files named by the manifest must be present under the
already-bound V10B durable attempt root. For each manifest entry, the
validator must verify the exact relative location, byte count, and SHA-256
against the preserved bytes. The locked payload set must contain no extra
payload files beyond the manifest's accepted entries, and the canonical
ticker order must remain intact where ordering applies.

This is a byte-integrity check only. V10C does not parse, transform, or
inspect the payload contents, prices, outcomes, targets, labels, returns, or
model features.

The future Phase-B adoption validator may read the exact 283 locked payload
files only to calculate byte count and SHA-256 and to establish exact
manifest closure. It must not JSON-parse payload price contents, inspect
OHLCV/prices, derive features, inspect labels/targets/outcomes/returns,
invoke the V4 Yahoo semantic parser, fit models, or perform T0/evaluation.
Safe stdout, stderr, state, logs, and receipts may contain only hashes,
counts, booleans, and bounded safe enums; they must not contain ticker
identities, raw payloads, prices, absolute machine paths, raw URLs, or human
authorization identity.

The candidate root is one future operational locator supplied to the
reviewed validator. It is not part of the scientific identity. The validator
must reject a missing or non-directory root, reject symlink/junction/reparse
escapes, inspect the full existing ancestor chain for reparse points as
required by repository governance, and never search or guess arbitrary
roots. It must never copy, move, delete, reset, overwrite, or resume the
candidate. Identity is established exclusively through the frozen content
and provenance hashes and bindings.

### 4.4 Network-audit closure

The network audit must validate the frozen V10B audit field set and retry
rules structurally: fixed provider/query/range, bounded attempts, exact
terminal status, redirect no-retry precedence, accepted/failed terminal
classification, and the exact observed record count of 300. Audit
validation must establish that the preserved payload set is closed and that
no post-terminal refetch or fallback occurred.

No Phase-B operating-system process-exit code is required or inferred by
this new adoption rule. The missing V10B exit-code evidence remains a
recorded V10B wrapper-evidence failure and is not rewritten as successful
V10B evidence.

### 4.5 Adoption PASS

Only when Sections 4.1–4.4 all pass may the candidate receive:

```text

V10C_TRAINING_INPUT_PROVENANCE=ADOPTED_FROM_V10B_LOCKED_ARTIFACT_SET
```

The adoption result is a new provenance identity. It is not a scientific
T0 result, not a strategy result, not profitability evidence, and not a
claim that the historical V9_009 cache was recovered.

## 5. Disjoint failure semantics

The offline validator must classify failures into exactly one of these
disjoint classes:

1. `GOVERNANCE_PROVENANCE_FAILURE` — repository, branch, reviewed commit,
   terminal-adjudication binding, or authority/preflight identity cannot be
   established.
2. `LOCKED_ARTIFACT_INTEGRITY_FAILURE` — receipt, manifest, payload-byte,
   partition, audit, hash, count, or closure contract fails.
3. `IMPLEMENTATION_FAILURE` — unexpected validator, filesystem wrapper,
   serializer, or other programming/runtime defect.

None is a strategy, data-quality, scientific, or profitability failure. No
class authorizes reacquisition. No class permits retry, fallback, repair,
or a second attempt. The missing V10B process-exit evidence remains a
historical `IMPLEMENTATION_FAILURE` / `WRAPPER_EVIDENCE_PROVENANCE_FAILURE`
fact and is not silently recategorized.

## 6. Promotion and immutability

After a future V10C offline PASS, the exact manifest SHA-256, attempt-receipt
binding, terminal-adjudication ancestry, and exact accepted payload set may
be promoted only as V10C training-input provenance. The promoted record must
retain ancestry to the V10B locked acquisition and must not be relabeled as
V9_009 historical-cache recovery. The exact bytes become immutable after
promotion; no post-outcome selection or payload refetch is permitted.

Promotion itself does not authorize T0, evaluation, model fitting,
backtesting, or profitability claims. A later T0 must have a separate
successor input-binding implementation requiring the exact promoted
manifest, GPT exact-SHA review, Phase-A preflight, and any fresh point-of-use
authority required by the applicable governance.

Promotion is mechanically closed by a separate durable
`V10C_TRAINING_PROVENANCE_ADOPTION_RECORD.json`; this record is not created
by this design remediation. The required sequence is:

```text
Phase B offline execution
-> Phase C safe inspection
-> GPT adoption adjudication
-> only if GPT adjudication PASS, create the adoption record in a separate
   bookkeeping/promotion task
-> commit
-> GPT exact-SHA review of that adoption record
-> only if that review PASS, mark V10C provenance ADOPTED
```

Before that final adoption-record GPT PASS, the state must remain
`V10C_TRAINING_INPUT_PROVENANCE=NOT_ADOPTED` and
`V10C_MANIFEST_ADOPTION_SHA256=NOT_PROMOTED`. Only after PASS may it become
`V10C_TRAINING_INPUT_PROVENANCE=ADOPTED_FROM_V10B_LOCKED_ARTIFACT_SET` with
manifest SHA-256
`887c031a004f91a080fa53ab511711fff92c92527cb119878ab2c295ee13cd44`.

The adoption-record schema is frozen at design level as
`V10C_TRAINING_PROVENANCE_ADOPTION_RECORD_V1` and must contain at least:

## 7. Frozen methodology and research integrity

V10C leaves unchanged the V4 universe and ticker-list identities, V9_009
features and D0 scoreability, D1/D2/D3 target semantics, evaluation and T0
years, model parameters, TOP1 selection, thresholds, costs/slippage,
portfolio mechanics, stopping rule, no-hyperparameter-search rule,
evaluation-cache identity, and V10A calendar authority.

There is no post-outcome selection, favorable ticker substitution,
threshold tuning, holdout/evaluation inspection, or methodology change.
Calendar authority is neither regenerated nor reopened. The adoption has
`profitability_evidential_capacity=ZERO`, and
`future_profitability_established=false`.

## 8. Authority and required sequence

This design task consumes no human gate and grants no execution authority:

```text
V10C_DESIGN_FROZEN=false
V10C_IMPLEMENTATION_AUTHORIZED=false
V10C_ADOPTION_EXECUTION_AUTHORIZED=false
V10C_T0_AUTHORIZED=false
V10C_HISTORICAL_EVALUATION_AUTHORIZED=false
V10C_PRIVATE_SEALED_ACCESS_AUTHORIZED=false
FRESH_V10C_OFFLINE_ADOPTION_AUTHORIZATION_REQUIRED=true
```

The frozen sequence is:

```text
DESIGN
-> GPT exact-SHA review
-> PASS with C=0/H=0/M=0
-> explicit human V10C design-freeze approval
-> durable design-freeze approval record
-> GPT review of that record
-> offline validator implementation
-> synthetic tests
-> GPT implementation review
-> Phase A NO-NETWORK durable-state preflight
-> GPT Phase-A adjudication PASS
-> fresh explicit human authorization scoped only to one V10C offline
   provenance-adoption execution
-> Phase B offline adoption execution exactly once
-> Phase C safe inspection
-> GPT adoption adjudication
```

The design-freeze authority and any later adoption-execution authority are
distinct and cannot be reused for each other. The fresh offline-adoption
authorization is required before the first locked payload byte read, is
consumed at that point-of-use boundary, and is not reusable for a second
adoption execution. It does not authorize network access, Yahoo refetch,
T0, evaluation, model fitting, backtesting, or private/sealed access.
V10B network authority, if any, does not transfer to V10C. After authority
consumption there is no retry, reset, delete, overwrite, or second attempt.

No step in this design grants T0, historical evaluation, private/sealed
access, network acquisition, or a profitability claim.
